# M3 demo checklist and staging runbook

What M3 delivers: voice channels in the web client, with permission-derived LiveKit grants, presence in the sidebar, an audio
pipeline (browser echo cancellation, RNNoise with a browser fallback, presets, mic test, push to talk in the window), a
connection test, `tincan doctor` network checks and a pinned LiveKit in the generated compose file. Built 2026-10-29. Spike
results, cuts and deferrals: [18 §J](../18-open-questions-and-risks.md#j-m3-build-notes-2026-10-29).

What has been run: every server rule by automated tests; the whole voice path by the **3-person media test** (real server, real
web client, real LiveKit, three headless Chromium clients on fake devices): join, Opus audio both ways with under 5 % loss,
presence, mute, deafen, app restart mid-call, a 3 s network drop, SPEAK revoked and restored, CONNECT revoked mid-call, leave. **Nothing has been run on a
real VPS, with real microphones, on a phone, in Firefox or Safari, behind Caddy's CSP, or through TURN.** Rows marked
**(VPS)** need the server, **(you)** need a person with a microphone, **(people)** need a second person on another network.

```bash
pnpm install

pnpm build && sh tools/media-test/docker.sh    # the 3-person media test; needs Docker, about 3 minutes the first time
```

- [ ] `pnpm check` is green.
- [ ] `sh tools/media-test/docker.sh` ends with `11/11 passed`. (On a Linux machine `pnpm media-test` does the same with host networking.)
- [ ] `pnpm vitest run --project unit apps/server/src/modules/voice`: grant table, hidden channel, limits, webhook races, reconciler repairs, fast path within 2 s.

## B. Staging deployment (VPS) — what you have to do

The firewall is yours to open; nothing below has been done for you. Replace `chat.example.com` with `mkarl.io`.

**1. Firewall.** In the provider's firewall (security group) **and** on the host (`ufw`) allow:

| Port | Why |
|---|---|
| **7881/tcp** | WebRTC over TCP, the fallback when UDP is blocked |
| **7882/udp** | WebRTC media. One port for everybody (18 T4), not a range |
| 5349/tcp | TURN over TLS, only if you set up the relay (step 4) |
| 3478/udp | TURN over UDP, same condition |

Keep **7880/tcp closed**: it serves LiveKit's admin API. Ports 80 and 443 stay as they are.

```bash
sudo ufw allow 7881/tcp && sudo ufw allow 7882/udp          # add 5349/tcp and 3478/udp for the relay
```

(Your SSH user has no sudo, so this is a step for you or the provider's console.)

**2. Update the deployment.** M3 changed the generated files. Either regenerate in a fresh directory
(`node apps/server/dist/cli.js init --dir ../tincan-m3 --domain chat.example.com --yes`, then move `data/` and keep your `.env` secrets), or
edit your existing `~/tincan` by hand:

- `.env`: add `TINCAN_LIVEKIT__API_URL=http://host.docker.internal:7880` (the other three `TINCAN_LIVEKIT__*` lines exist already).
- `docker-compose.yml`, service `tincan`: add
  ```yaml
      extra_hosts:
        - "host.docker.internal:host-gateway"
  ```
  and in service `livekit` replace `image: livekit/livekit-server` with `image: livekit/livekit-server:v1.13.10`.
- `livekit.yaml`: set `bind_addresses` to `127.0.0.1` and `172.17.0.1` (see the generated file in `tincan init`'s output for the full shape), the webhook URL to
  `http://127.0.0.1:3000/api/v1/internal/livekit/webhook`, and `rtc.use_external_ip: true`, `udp_port: 7882`.
- `Caddyfile`: replace the `/api/internal/*` block with
  ```
  	@internal path /api/internal/* /api/v1/internal/*
  	handle @internal {
  		respond 404
  	}
  ```
  and add `'wasm-unsafe-eval'` after `script-src 'self'` in the CSP header.

**3. Start it.**

```bash
cd ~/tincan-src && git fetch && git checkout <the M3 branch or commit> && cd ~/tincan
docker compose build tincan caddy && docker compose --profile voice up -d
docker compose logs --tail 30 livekit tincan
node ~/tincan-src/apps/server/dist/cli.js doctor --config ~/tincan/config.yaml     # or: docker compose exec tincan node dist/cli.js doctor
```

- [ ] **(VPS)** `doctor` shows `Voice server reachable` ok, `Webhook path` ok (loopback answers 401, public URL answers 404), `Public IP matches` ok or an explained warning.
- [ ] **(VPS)** From **another machine**: `nc -vz chat.example.com 7881` succeeds. (UDP cannot be checked this way; the in-app test below is the real one.)
- [ ] **(VPS)** `docker compose logs livekit` shows no `could not` or `error` lines after start.

**4. Optional: the relay (TURN over TLS).** Needs a second DNS name pointing at the VPS (`turn.chat.example.com`), ports 5349/tcp and
3478/udp open, and certificates from Caddy:

```bash
tincan init --dir /tmp/preview --domain chat.example.com --turn-domain turn.chat.example.com --yes   # shows the Caddyfile/livekit.yaml lines to add; do not overwrite your .env
docker compose up -d caddy && docker compose logs caddy | grep -i "turn.chat"       # wait for "certificate obtained"
docker compose --profile voice restart livekit
node ~/tincan-src/apps/server/dist/cli.js doctor --config ~/tincan/config.yaml --turn-domain turn.chat.example.com
```

- [ ] **(VPS)** `Relay (TURN/TLS 5349)` is ok with the certificate's remaining days. When Caddy renews (about every 60 days), run
  `tincan voice turn-reload --turn-domain turn.chat.example.com` from cron daily: it restarts LiveKit only when no call is running, or within 7 days of expiry (`--apply` to do it).

## C. Voice in the browser (you)

- [ ] **Join.** Click **Lounge** in the sidebar: the call view opens, the dock shows "Voice connected · Lounge", and you appear under Lounge with your avatar. The browser asks for the microphone once.
- [ ] **Others.** A second person (other browser or device) joins: both sidebars list both people within a second or two; each tile shows a ring while that person speaks (and "… is speaking" for screen readers). The ring is on the right person, not shifted.
- [ ] **Hearing.** You hear the other person; they hear you. Say something quiet and something loud: no clipping, no pumping.
- [ ] **Mute / deafen.** Mute: the other person sees the crossed microphone within a second and stops hearing you. Deafen: you hear nothing, they see the headphone icon. Undeafen restores your mic only if you had not muted yourself.
- [ ] **Per-person volume.** In the call view, the slider on someone's tile changes how loud only they are for you, and survives a reload.
- [ ] **Leave.** The leave button clears you from the sidebar for the others at once. Closing the tab clears you within about 20 seconds.
- [ ] **One place at a time.** Join Lounge, then another voice channel: you leave the first. Join from a second device: the first shows "You joined from another device".
- [ ] **Text keeps working** during a call, and joining voice does not change the text channel you are reading.

## D. Audio (Settings › Voice & audio) (you)

- [ ] The **input** and **output** pickers list your devices by name. Unplug the chosen microphone: the call goes on with the default; plug it back in and pick it again.
- [ ] **Mic test:** record 5 seconds, play back *with* and *without* processing. With processing, a fan or keyboard is quieter and your voice is not underwater. **Please judge this by ear; it is the one thing I could not measure** (18 §J D2-3).
- [ ] **Sound profile:** Standard, Aggressive, Natural, Studio / Music each change what you hear on playback; Studio warns about headphones; touching an Advanced control switches the profile to Custom.
- [ ] **Noise suppression** set to Browser built-in and to Off both work. If the denoiser cannot load (blocked WebAssembly) a notice says it fell back to the browser's.
- [ ] **Echo:** speakers instead of headphones, two people in the call: the other person does not hear themselves.
- [ ] **Push to talk:** switch the transmit mode, press the key in the app window: the dock shows "Hold F to talk" and the other person hears you only while it is held plus the release delay. Alt-tab away while holding: it lets go. Typing in the message box does not trigger it.
- [ ] **CPU:** with the denoiser on, a call for five minutes on your slowest machine stays below roughly 10 % CPU in the browser's task manager. If it is much higher, say so: that decides whether tier A is needed.

## E. Connection test (W-25) (you, people)

- [ ] **Settings › Voice & audio › Run test** on a normal network: server, microphone, direct connection (UDP) ok; the summary says it works over a direct connection; **Copy diagnostics** puts text on the clipboard.
- [ ] **(people)** From a network that blocks UDP (phone hotspot with a restrictive carrier, a work network, or a VPN that blocks it): the test reports the direct path blocked, the backup connection (TCP) ok, and the dock says "Connection: backup (TCP)". A call still works with a little more delay.
- [ ] **(people, VPS, after step B4)** From a network that allows only 443: the test reports the relay ok. **This is the only place TURN gets tested for real** (18 §J D6-4).
- [ ] Block the voice ports on the server (or stop LiveKit): the test says voice does not work here and text does.

## F. Permissions during a call (you)

- [ ] As admin, in Settings › Channels › Lounge › Permissions, deny **Speak** for a member who is in the call: within a couple of seconds they can no longer be heard. Allow it again: they are heard again without rejoining.
- [ ] Deny **Connect** for someone in the call: they are removed within seconds and see "You no longer have permission to be in this voice channel". The others' sidebars update.
- [ ] Deny **View channel**: Lounge disappears for them and they are removed.
- [ ] Set the channel's **user limit** to 2 (channel settings JSON; there is no UI field yet): a third person gets "This voice channel is full".

## G. Failure behaviour

- [ ] `docker compose restart tincan` during a call: nobody drops; the sidebar is correct again within a few seconds (reconciler).
- [ ] **(VPS)** `docker compose --profile voice restart livekit` during a call: the clients show "Voice disconnected" with **Rejoin**; text chat is unaffected.
- [ ] Switch Wi-Fi off and on for 5 seconds during a call: "Reconnecting…", then connected again, without rejoining by hand.
- [ ] `curl -s https://chat.example.com/api/v1/internal/livekit/webhook -X POST` answers 404 from outside.
- [ ] **(VPS)** After a day with a few calls: `GET /api/v1/voice/status` (as owner) shows `repairs` close to zero apart from after restarts. A steady count of `presence_added` or `presence_removed` means webhooks are not arriving (check the webhook URL and `bind_addresses`).
