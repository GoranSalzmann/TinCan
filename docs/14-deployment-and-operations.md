# 14. Deployment & Operations

How a Host installs, runs, monitors, backs up, upgrades and troubleshoots Tin Can.
Target: N-006, a blank VPS to a working instance in under 15 minutes. Port numbers,
config keys and image names are **proposed** and must be confirmed against pinned
LiveKit/Caddy versions in spike D6 (T11).

## 1. Hosting prerequisites

| Requirement | Detail |
|---|---|
| OS | Linux x86-64 or arm64 recommended (Debian/Ubuntu LTS). Windows/macOS hosts via Docker are possible for testing but not recommended for production (UDP/host-network quirks) |
| Docker | Docker Engine + Compose v2 |
| Domain | A DNS name pointing at the server (e.g. `chat.example.com`); optional second name for TURN (`turn.example.com`) |
| Ports | See §3 |
| Public IP | Required for media. **CGNAT / no port-forwarding** (some home ISPs) breaks direct hosting: use a VPS, or a VPS relay/tunnel for UDP (documented, not first-class) |
| Bandwidth | Sized per 08 §5.5; unmetered or high-allowance plan recommended |
| Sizing | 1–2 vCPU, 1–2 GB RAM, 10+ GB disk is enough for a friends-scale instance; bandwidth is the real constraint |

Home hosting is supported if the Host can forward ports and has a public
IPv4 (or IPv6 with working inbound). The doctor command detects CGNAT symptoms
(§9) and explains options.

## 2. Components and compose topology

```
 services:
   caddy       TLS, reverse proxy, serves web client static files
   tincan      app server (Node)
   livekit     SFU + TURN (host networking recommended on Linux)
   redis       optional (profile: "recording"; LiveKit Egress needs it)
   egress      optional (profile: "recording")
 volumes: ./data (db, files, setup-token), ./caddy-data, ./config
```
- `tincan` image runs as non-root, read-only root filesystem where possible, with `/data` writable.
- `livekit` with **host networking** avoids Docker's UDP NAT overhead and port-mapping pitfalls on Linux; the compose file documents the bridge-network alternative (needs explicit UDP port publish).
- **Routing with host networking (18 T26).** A host-networked container is not on the compose network, so Docker service names don't resolve to or from it. The app is published on `127.0.0.1:3000` and LiveKit posts its webhooks there; Caddy and the app reach LiveKit through the Docker host gateway (`host.docker.internal`, via `extra_hosts: host-gateway`). LiveKit's HTTP port 7880, which also serves the RoomService admin API, must not listen on the public interface: bind it to loopback and the host-gateway address (verify the setting, and that it leaves the RTC ports alone, in D6), and keep it closed in the firewall (§3) as a second layer.
- Optional services are enabled through compose profiles so the default stack is minimal: `caddy + tincan + livekit` (SQLite, in-memory pubsub, local storage). Redis comes in for recording (LiveKit Egress) or multi-node LiveKit; the app's own Redis adapter is post-v1 (18 T32).

### 2.1 Reverse proxy routes (Caddy)
| Path | Target |
|---|---|
| `/api/*`, `/gateway`, `/files/*` | `tincan:3000` (WebSocket upgrade supported) |
| `/livekit/rtc*` (signalling WSS only) | LiveKit at `host.docker.internal:7880`. Other LiveKit HTTP routes, including the Twirp RoomService admin API, are not proxied (18 T26) |
| everything else | static web client (`/srv/web`) with SPA fallback |
| `/api/internal/*` | **blocked** from the public; LiveKit (host networking) posts webhooks to the app's loopback-published port `127.0.0.1:3000` (T5, T26) |
Security headers (HSTS, `X-Content-Type-Options`, `Referrer-Policy`, CSP, `Permissions-Policy` allowing camera/mic/display-capture for self) are set in the Caddyfile (15).

Example Caddyfile sketch:
```
chat.example.com {
  encode zstd gzip
  handle /api/internal/* { respond 404 }
  handle /api/* { reverse_proxy tincan:3000 }
  handle /gateway { reverse_proxy tincan:3000 }
  handle /files/* { reverse_proxy tincan:3000 }
  handle /livekit/rtc* { uri strip_prefix /livekit; reverse_proxy host.docker.internal:7880 }
  handle { root * /srv/web; try_files {path} /index.html; file_server }
  header { Strict-Transport-Security "max-age=31536000"; ... }
}
```

### 2.2 LiveKit config sketch (verify keys)
```yaml
port: 7880
rtc:
  tcp_port: 7881
  udp_port: 7882          # single-port mux
  use_external_ip: true   # or node_ip: <public ip>
turn:
  enabled: true
  domain: turn.example.com
  tls_port: 5349
  udp_port: 3478
  cert_file: /certs/turn.crt
  key_file:  /certs/turn.key
keys:
  <apiKey>: <apiSecret>   # generated by `tincan init`
webhook:
  api_key: <apiKey>
  urls: ["http://127.0.0.1:3000/api/internal/livekit/webhook"]   # host networking: no Docker DNS (T26)
# redis: only when needed
```

### 2.3 TLS for TURN (resolves T3 proposal)
- Primary web/WSS traffic is TLS-terminated by Caddy on 443.
- LiveKit's TURN/TLS needs its own certificate. v1 approach: a `turn.example.com` name served by Caddy only for certificate issuance; the issued cert/key files are made available to LiveKit through a shared read-only volume (a small helper copies Caddy's certificate files for that hostname). LiveKit reads the certificate only at start (no hot reload; verify in D6), and restarting it drops every call (§5), so the helper **defers the reload** (18 T30): after a renewal it restarts LiveKit only when no rooms are active (checked through LiveKit's `ListRooms` API), or, if rooms never empty, once the certificate LiveKit is using is within 7 days of expiry, preferring a configured quiet window. Caddy renews about 30 days before expiry, so in practice the restart lands in an empty moment. TURN/TLS listens on **5349**.
- Many restrictive networks only allow outbound 443. Advanced option: serve TURN/TLS on 443 on a **separate IP** or via an SNI-based TCP router (Caddy layer4 plugin / HAProxy / nginx stream). Documented as optional; validated in spike D6. Real-world impact is measured by the connectivity diagnostics (08 §10): the percentage of users who need TURN/TLS on 443 will be small.

## 3. Firewall / network checklist

| Port | Proto | Needed for | Required |
|---|---|---|---|
| 80 | TCP | ACME HTTP challenge / redirect | Yes |
| 443 | TCP (+UDP for HTTP/3 optional) | Web, API, WebSocket, LiveKit signaling | Yes |
| 7881 | TCP | WebRTC TCP fallback | Yes |
| 7882 | UDP | WebRTC media (mux) | Yes |
| 3478 | UDP | TURN/STUN | Recommended |
| 5349 | TCP | TURN/TLS | Recommended |
Cloud firewall (security groups) AND host firewall (ufw/nftables) must both allow
these; the docs include copy-paste ufw rules and provider-specific notes.
`tincan doctor` checks reachability from outside using a lightweight probe
service option or a self-test instruction ("run this command from another machine").

## 4. Installation flow

1. Point DNS (A/AAAA) for `chat.example.com` (and `turn.example.com`) at the server.
2. On the server: download the **signed release bundle**, verify its checksum and signature (the docs show the exact commands), extract it, and run `./tincan init` (it prints what it will do before changing anything). A convenience one-liner (`curl -fsSL https://<project>/install.sh | sh`) is documented as a secondary option; it only downloads and verifies the same signed bundle and then stops, so it adds no trust beyond the bundle itself.
3. `tincan init` asks: domain, admin email for ACME, enabled features (defaults on), E2EE default (on); the database and storage are SQLite and local disk in v1 (18 T32). It generates: `.env`/secrets (LiveKit key/secret, instance secret, session secrets) with 0600 permissions, `config.yaml`, `docker-compose.yml`, `Caddyfile`, `livekit.yaml`.
4. `docker compose up -d` (init can run it).
5. Open `https://chat.example.com/setup`, enter the **setup token** printed by `tincan init` (also in `./data/setup-token`), create the owner account (11 §1.4).
6. `tincan doctor` runs the self-test; the setup page also shows a checklist (HTTPS OK, WebSocket OK, LiveKit reachable, UDP reachable, TURN reachable, external IP matches).
7. Create an invite link; share with friends.

Manual path (no script) is documented step by step for people who prefer it.

## 5. Configuration management

- Single `config.yaml` (04 §9), env overrides, secrets via env / `*_FILE`.
- Secrets inventory: LiveKit API key & secret, instance secret (E2EE derivation, 10), session/CSRF signing key, OIDC client secret, S3 credentials, Redis password, SMTP (future). Stored in `.env`/Docker secrets with restrictive permissions; never in the image; never logged.
- `tincan config check` validates and prints the resolved module/adapter graph.
- Config changes require a restart (`docker compose restart tincan`), except LiveKit settings (restart LiveKit; calls drop).
- Environment parity: the same compose files for dev (with a dev override) and prod.

## 6. Data layout & backups

```
data/
  app.db (+ -wal, -shm)    SQLite database
  files/                   attachments, avatars (local storage adapter)
  setup-token              deleted after setup
  backups/                 snapshots (if scheduled)
config/  config.yaml, livekit.yaml, Caddyfile
.env     secrets
caddy-data/  ACME account & certificates
```
- **Backup set:** database snapshot + files + `config/` + `.env` (secrets are needed to keep E2EE derivation and API keys; protect the backup).
- `tincan backup` produces a timestamped archive: a SQLite snapshot via `VACUUM INTO` from the CLI's own connection (consistent while the server keeps writing, without stalling it, 06 §7), files (rsync-style or tar), config. (`pg_dump` and S3 bucket versioning apply once those post-v1 adapters exist.)
- Scheduled via the `backup.hook` job (05 §7) or host cron; retention settings (e.g. keep 7 daily, 4 weekly); optional upload to another storage target (S3/rclone).
- `tincan restore <archive>` into an empty directory; steps documented; **CI tests restore** (16).
- Recommend off-host copies; docs include a 3-2-1 reminder.

## 7. Upgrades

- Images are tagged with explicit versions (`tincan:1.2.3`); `latest` not recommended. Pinned LiveKit version tested with each Tin Can release (compatibility matrix in release notes).
- Procedure: `tincan backup` → read release notes → bump versions → `docker compose pull && docker compose up -d`. Migrations run automatically at boot (06 §8) after an automatic pre-migration backup (the same `VACUUM INTO` snapshot, not a file copy, 06 §8).
- Zero-downtime is not a goal; expected downtime seconds. LiveKit restarts drop calls; the app server restart doesn't.
- Rollback: restore the pre-upgrade backup and previous image tag (the server refuses to start on a newer schema, 06 §8, to prevent silent corruption).
- Desktop clients update independently; `apiVersion` negotiation covers skew (07 §6). Release notes flag breaking protocol changes and the minimum client version.
- Optional "update available" notice for admins in the UI (checks a public version feed; **off by default, no telemetry**; opt-in).

## 8. Observability

- **Logs:** JSON to stdout, collected by Docker (`json-file` with rotation limits set in compose). Request IDs, user IDs (not tokens), module names. Log level via config.
- **Metrics:** module `metrics` exposes `/metrics`, bound to an internal listener or token-protected: HTTP rates/latency, gateway connections, events/s, DB latency, job durations, voice participants/rooms, webhook lag, reconciler repairs by kind, outbox backlog, LiveKit reachability. LiveKit also exposes Prometheus metrics (verify config) for CPU, bandwidth, packet loss, room counts.
- **Dashboards:** an optional compose profile adds Prometheus + Grafana with provisioned dashboards (not default).
- **Health:** `/healthz`, `/readyz` (07, 05 §8), Docker `HEALTHCHECK`, optional external uptime check.
- **Alerts (docs recommend):** disk > 80%, certificate expiry < 14 days, 5xx rate, LiveKit down, egress near plan limits, a sustained non-zero rate of reconciler repairs (a primary path such as webhooks is broken; 18 T34), a TURN certificate reload still pending within 10 days of expiry.
- **Admin dashboard (in-app):** `GET /admin/stats` surfaces users, storage, active voice rooms, current egress estimate, and warnings (e.g. "External IP changed").

## 10. Scaling & high availability (not v1 goals, not blocked)

| Step | Change |
|---|---|
| More voice capacity | Larger VPS with more bandwidth; or run LiveKit on a separate host (topology C) |
| Multiple app nodes | Postgres + Redis (post-v1 adapters, 18 T32), load-balanced gateway with sticky-less resume (the resume ring buffer is per node, so use sticky sessions by `sessionId` hash or store ring buffers in Redis; decision when needed) |
| Multiple LiveKit nodes | Shared Redis, region routing via LiveKit's multi-node support |
| Object storage | S3-compatible adapter (post-v1) |
HA failover and Kubernetes manifests/Helm chart are out of scope for v1 (community
contribution candidate).

## 11. Security hardening checklist for Hosts

- Keep the OS and Docker updated; unattended security upgrades.
- Firewall closed except §3 ports; SSH keys only, no root login; fail2ban optional.
- Do not expose Redis, Postgres or LiveKit's HTTP port 7880 (it also serves the RoomService admin API); internal network or loopback only (§2).
- Back up `.env` securely; rotate secrets on staff/friend changes if relevant.
- Keep `signup: invite-only` unless intentionally public.
- Restrict `/metrics`.
- Review logs for repeated auth failures.
Details of the threat model in 15.

## 12. Troubleshooting guide (docs outline)

| Symptom | Likely cause | Check |
|---|---|---|
| Can log in, cannot join voice | LiveKit unreachable / wrong URL / WSS blocked | `doctor`, browser console, `/livekit` proxy |
| Joins but no audio / one-way audio | UDP blocked or wrong external IP | `use_external_ip`, firewall, TURN fallback working? client "Test connection" |
| Works on Wi-Fi, fails on mobile data/corporate | Needs TURN/TLS | open 5349; consider 443 option |
| Choppy screenshare | Publisher upload low / server egress saturated | choose lower preset; check metrics |
| Certificate errors | DNS/ACME failure, port 80 closed | Caddy logs |
| Echo/noise complaints | Client audio settings | 09 presets, headphones |
| After upgrade fails to boot | Migration error | pre-migration backup, logs |
| Presence stuck or lagging ~30 s | Webhooks not arriving | webhook URL (`127.0.0.1:3000` with host networking, §2); a rising `reconcile_repairs_total` confirms it |

## 13. Development & staging environments

- `pnpm dev` + `docker compose -f compose.dev.yml up livekit` (LiveKit in dev mode, keys `devkey/secret`, no TLS) for local work. Browser media permissions work on `localhost` without HTTPS.
- A staging compose using real DNS and certs to test TURN, UDP and E2EE (secure contexts require HTTPS for getUserMedia/WebCrypto off-localhost).
- Seed command to create fake users, channels, messages.

## 14. Release & image build

- CI builds multi-arch (amd64/arm64) images, scans them (Trivy/Grype), signs (cosign), publishes to GHCR (and Docker Hub optional); SBOM attached (15).
- Release bundle includes compose templates, `tincan` CLI, checksums, SPDX/licence files, and the corresponding-source link (AGPL).
