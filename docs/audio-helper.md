# Linux application audio

Tin Can stays a PWA. A small Rust companion adds selected-application audio on
Linux x86-64, including games and media players. Video still uses the browser's
screen picker; application audio is a separate stereo LiveKit `ScreenShareAudio`
publication. The normal microphone publication is unchanged.

## User setup

1. Join a call in a current Chromium-based browser.
2. Open **Share your screen**, enable **Share audio**, then choose **Application audio**.
3. Use the download or terminal installer shown there. The archive contains a
   static musl executable; extraction followed by `./tincan-audio install` installs
   it for the current user and enables XDG desktop autostart.
4. Choose **Check again → Connect helper**. Confirm the **exact Tin Can server**
   on the local page, then return to the PWA. Allow local-network access and
   audio-device access if the browser asks.
5. Play audio in the desired app, select its streams, and press **Continue**.
   Choose the video in the browser's picker. The sharing bar shows selected apps
   and a live audio meter.

The local approval tab intentionally stays open after confirmation; it is safe
to close. Pairing polling works with the PWA's COOP isolation, without an opener.
The helper management page is at `http://127.0.0.1:19477`.

### Requirements and boundaries

- Linux x86-64 with PipeWire, `pipewire-pulse`, a session manager (usually
  WirePlumber), and `pw-dump`, `pw-link`, `pw-loopback` on the helper's `PATH`.
- Chromium with `AudioContext.setSinkId`. Firefox/Safari and PulseAudio-only
  desktops do not support this path. Windows continues to use the browser
  capture path and requests Chromium's `restrictOwnAudio`; that constraint is
  browser/OS dependent and is not a portable exclusion guarantee.
- Sandboxed browsers need access to the desktop's audio devices and localhost.
  Snap/Flatpak permissions and device discovery vary; these packages have not
  all been qualified.
- Each checkbox selects an **existing playback stream**, not a process-wide
  identity or a system monitor. An app can have several streams, and a browser
  can combine several tabs into one stream. Closing/restarting a stream requires
  restarting the share and selecting its new stream. The UI reports missing
  selections; it never silently selects an unrelated stream.
- There is no “all system audio” checkbox. Select up to 32 application streams.
  Stereo FL/FR and mono streams are supported; other surround channels are not
  downmixed into the share.
- Changing the Tin Can output or losing the protected output stops sharing and
  restores normal conversation playback. The call itself remains connected.
  Do not manually reroute the helper's devices with a graph editor.

## Installation, updates and removal

The installation is in `~/.local/lib/tincan-audio`; launcher and autostart use
the XDG data/config directories. Run the installer again to update. It stops the
installed process and atomically replaces the executable before restarting.

```sh
~/.local/lib/tincan-audio/tincan-audio doctor
~/.local/lib/tincan-audio/tincan-audio stop
~/.local/lib/tincan-audio/tincan-audio uninstall
```

Uninstall stops the helper, removes its binary, launcher, autostart, logs and
pairings. The browser's saved token then expires on its next request.
Configuration is `$XDG_CONFIG_HOME/tincan-audio/sites.json` (0600);
logs/PID are in `$XDG_STATE_HOME/tincan-audio`. Default XDG fallbacks apply.
The installer downloads from the current Tin Can server and verifies the
archive against that server's `SHA256SUMS`.

## Server upgrade

The `web` Docker target builds and includes the helper archive, checksum and
installer at `/helpers/`. The GitHub release also attaches the archive and
installer. The helper is built for **x86-64 even in the ARM64 web image**.

Existing reverse-proxy configurations must add the exact helper address to the
PWA's CSP `connect-src`:

```text
http://127.0.0.1:19477
```

New Caddy configurations generated by Tin Can include it. Existing generated
Caddyfiles are not automatically overwritten: update this directive in the
active file and reload Caddy. Do not proxy the helper through the Tin Can server;
it runs on each sharing person's computer.

For a non-Docker web build, build/package the helper before `pnpm build`:

```sh
cargo build --locked --release --target x86_64-unknown-linux-musl --manifest-path apps/audio-helper/Cargo.toml
sh scripts/package-audio-helper.sh apps/audio-helper/target/x86_64-unknown-linux-musl/release/tincan-audio apps/web/public/helpers
pnpm build
```

Generated archives/checksums and Rust build output are gitignored.

## Audio path

1. The helper resolves the current/preferred physical output and creates two
   `pw-loopback` pairs:
   - selected application output ports → unconnected capture input → **Tin Can
     Stream `<session>`**, a virtual stereo source;
   - **Tin Can Call `<session>`**, a virtual sink → the original output.
2. Both virtual devices have negative session priority, so session-manager
   default selection cannot redirect unrelated playback into them.
3. The PWA opens the **exact virtual input device ID**, disables browser speech
   processing, then routes its conversation `AudioContext` to the dedicated sink.
4. Only after routing and the lifetime watch are established does it request
   native capture and publish the track. Microphones, monitors, helper nodes and
   streams targeting/linked to the conversation sink are excluded natively.
5. Explicit stop first stops outgoing samples, restores the previous output,
   and deletes the native session. Output routing changes synchronously disable
   outgoing samples before asynchronous cleanup.

For listen-only users, a short unpublished permission stream may be opened to
unlock device labels and immediately stopped. It is never used as shared audio.
Exact-device acquisition has no microphone/default-device fallback.

Selection uses PipeWire `object.serial`, not recyclable registry node IDs.
Links are recomputed from snapshots; lost applications produce silence rather
than being replaced by newly created nodes. A helper/watch failure, revoked
publication, room departure or picker cancellation releases owned resources.
Late asynchronous browser results are cleaned up against their original room.
Native children use `kill_on_drop` plus Linux `PR_SET_PDEATHSIG` so SIGKILL or a
helper crash also destroys the virtual devices and their links.

## Local protocol v1

HTTP binds **only** `127.0.0.1:19477`. Host checks reject DNS rebinding;
origins must be exact HTTPS origins (HTTP loopback is allowed for development).
No wildcard CORS, cookies, credentialed fetches or network audio uploads are used.
Each site gets a random 256-bit bearer capability after a CSRF-protected local
approval. Tokens are stored locally and checked with the request's exact origin.

| Route | Use |
| --- | --- |
| `GET /v1/status` | Protocol/version and PipeWire diagnostics; public |
| `GET /connect?origin=…&challenge=…` | Local approval page; challenge is 256-bit random hex |
| `POST /approve` | Local form confirmation with its generated CSRF value |
| `POST /v1/pair` | Origin-bound, one-time collection of the approved token |
| `GET /v1/sources` | Current application streams; authenticated |
| `POST /v1/session` | Creates virtual devices; body `{outputLabel}` |
| `GET /v1/session/{id}/watch` | Authenticated NDJSON lifetime/status stream |
| `POST /v1/session/{id}/start` | Selects streams; body `{sources: ["object.serial", …]}` |
| `DELETE /v1/session/{id}` | Stops capture and removes devices |

Only one session is allowed per helper. A session whose watch never opens is
removed after 30 seconds. Closing the watch removes its session; no background
JavaScript heartbeat is needed. Pairing expires after two minutes and is bound
to the requesting origin. The local management page can revoke all sites and
stop capture.

## Verification

`cargo test` covers graph exclusion, reused IDs, mono routing, exact origins,
Host/CORS checks, approval CSRF, token persistence and one-time origin-bound
pairing. Frontend tests cover exact-device acquisition, cancelled and late
`getUserMedia`/`setSinkId`/session creation, watch failure, immediate output-loss
cutoff, selection gating, inline failures, and room-scoped manager cleanup.

The real PipeWire test is `tools/audio-helper-test/run.py`. It creates a private
daemon/graph with distinct left/right, conversation and unselected tones,
measures captured samples and checks explicit stop, closed watch, SIGKILL and
install/update/uninstall. The same static binary passes on Ubuntu 24.04
(PipeWire 1.0.5, WirePlumber 0.4.17) and Fedora 44 (PipeWire 1.6.11, WirePlumber
0.5.19). This checks the distribution audio stacks, not every desktop/sandbox
combination.

Browser integration (`AUDIO_HELPER_BROWSER=1`) runs the PWA's actual client in
Chromium against the isolated PulseAudio/PipeWire devices. It passes pairing
under COOP, virtual-device discovery, separate left/right frequencies,
conversation exclusion and output restoration. The reusable
`.github/workflows/audio-helper.yml` runs Rust checks, both distribution stacks,
the HTTP download installer and this browser test for PRs and releases.

To run the browser test after building the helper and installing the workspace
dependencies:

```sh
docker build -f tools/audio-helper-test/Dockerfile.fedora -t tincan-audio-test-fedora .
docker build -f tools/audio-helper-test/Dockerfile.browser -t tincan-audio-test-browser .
docker run --rm -v "$PWD:/repo:ro" tincan-audio-test-browser apps/audio-helper/target/x86_64-unknown-linux-musl/release/tincan-audio
```

Before release, also exercise a physical headset, output unplug/reconnect,
screen permission loss, tab closure, and a second viewer listening to shared
music while speaking. Browser-specific screen pickers and physical hardware
remain part of manual QA.
